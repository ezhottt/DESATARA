# DATA DICTIONARY — DESATARA

**Document:** `docs/DATA-DICTIONARY.md`  
**Version:** 1.0  
**Status:** CONTROLLED BASELINE
**Parent:** ERD DESATARA v1.0  
**Database:** PostgreSQL  
**Application:** Laravel + Inertia.js + Vue 3  
**Tenancy:** Shared Database / Shared Schema / Tenant Isolation by `tenant_id`

---

# 1. PURPOSE

Data Dictionary merupakan physical-data contract DESATARA sebelum migration Laravel dibuat.

Dokumen ini menetapkan:

- PostgreSQL data types;
- primary keys;
- public identifiers;
- tenant ownership;
- foreign keys;
- composite tenant foreign keys;
- nullability;
- default values;
- unique constraints;
- check constraints;
- indexing baseline;
- delete/update behavior;
- historical mutability;
- concurrency controls;
- idempotency controls;
- sensitive fields;
- snapshot boundaries.

Migration tidak boleh memperkenalkan struktur yang bertentangan dengan dokumen ini tanpa controlled architecture change.

---

# 2. GLOBAL TYPE CONVENTIONS

| Semantic | PostgreSQL |
|---|---|
| Internal PK | `bigint GENERATED BY DEFAULT AS IDENTITY` |
| Public UUID | `uuid` |
| Short code | `varchar(n)` |
| Human text | `text` |
| Boolean | `boolean` |
| Date | `date` |
| Timestamp | `timestamptz` |
| Monetary value | `numeric(19,2)` |
| Quantity | `numeric(19,4)` |
| Version counter | `integer` |
| Snapshot payload | `jsonb` |
| IP address | `inet` |
| Hash/checksum | `varchar(128)` |
| Token hash | `varchar(128)` |

Laravel `timestamps()` without timezone must not silently become the architecture default.

Authoritative timestamps use timezone-aware database columns.

---

# 3. GLOBAL COLUMN CONVENTIONS

Tenant-owned transactional tables normally include:

```text
id
tenant_id
created_at
updated_at
```

Critical actor-aware tables additionally use appropriate:

```text
created_by
updated_by
```

Historical event tables may intentionally omit `updated_at`.

---

# 4. PUBLIC IDENTIFIERS

UUID is required for resources that may be:

- exposed in URL;
- exposed through API;
- exported externally;
- referenced asynchronously;
- used outside trusted internal DB context.

Internal `bigint` PK remains internal.

UUID must not replace regulatory/business numbers.

---

# 5. TENANT COMPOSITE KEY STANDARD

Tenant-owned parent tables must normally expose:

```sql
UNIQUE (tenant_id, id)
```

Tenant-owned child relation:

```sql
FOREIGN KEY (tenant_id, asset_id)
REFERENCES assets (tenant_id, id)
```

This pattern is mandatory where cross-tenant reference would create a security or integrity failure.

---

# 6. DELETE POLICY

Default FK behavior:

```text
ON UPDATE RESTRICT
ON DELETE RESTRICT
```

`CASCADE` is allowed only for dependent configuration/staging records whose independent historical existence has no business meaning.

Historical transaction tables do not cascade-delete.

---

# 7. STATUS IMPLEMENTATION

Critical statuses use:

- `varchar`;
- database `CHECK`;
- application enum/value object.

PostgreSQL native ENUM is not the default because regulatory/workflow evolution may require controlled value migration.

# 79. OPTIMISTIC LOCKING

Critical mutable aggregate uses:

```text
lock_version integer NOT NULL DEFAULT 1
```

Update semantics:

```text
UPDATE ...
WHERE id = ?
AND tenant_id = ?
AND lock_version = expected_version
```

Successful update increments version.

Zero affected rows → stale state/conflict.

# 88. REPORT IMMUTABILITY

When `asset_reports.status = finalized`:

- business fields cannot mutate;
- template version cannot change;
- reporting period cannot change;
- snapshot cannot change;
- artifact replacement cannot silently occur.

Correction creates revision.

# 89. WORKFLOW IMMUTABILITY

Published workflow version cannot be edited.

Existing workflow instance retains original `workflow_version_id`.

New version applies only according to effective-date/migration policy.

# 90. AUTHORITY IMMUTABILITY

Current official record may expire/revoke.

Historical authority snapshot remains unchanged.

Critical historical action must not reconstruct authority solely from current `tenant_officials`.

---

# 91. INVENTORY IMMUTABILITY

Expected inventory snapshot represents state at `reference_at`.

Later master changes do not rewrite expected snapshot.

Observed verification and reconciliation history remain traceable.
